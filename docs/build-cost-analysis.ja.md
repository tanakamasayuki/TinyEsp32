# ESP32 Arduino の処理別ビルド費用と設定の自由度

調査日: 2026年11月22日。Arduino CLI 1.5.1、Arduino ESP32 3.3.13、ESP32-S3 の既定設定を測定対象とする。対象チップや TinyEsp32 の実装方式を選ぶための測定用構成であり、S3 を開発対象に決定したものではない。

## 数値から分かった重い箇所

**初回は、最終アプリで使わないものも含めたコア全体のコンパイルが大きい。スケッチ変更時は、重い公開ヘッダーを繰り返し読む処理とリンクが大きい。変更なしでも、リンクとイメージ生成を再実行している。** 三つを同じ原因として扱わない。

| 観点 | 測定結果 | 改善対象として意味すること |
| --- | --- | --- |
| 初回のコア | 60ファイル、各3回の中央値の合計37.186 CPU秒 | ビルド対象と共有ヘッダーを減らす余地が大きい |
| そのうち C++ | 26ファイル、28.773 CPU秒、77.4% | C の小さな空ファイルを減らすだけでは不十分 |
| 最小アプリにコード・通常データが残らない側 | 50ファイル、27.843 CPU秒、74.9% | 未使用実装をコンパイル対象から外す境界に価値がある |
| `Arduino.h` だけの空の C++ | 1.324 CPU秒、前処理後68,611行 | ユーザーの処理が小さくても入口が重い |
| ArduinoCore-API だけの空の C++ | 0.497 CPU秒、24,407行 | Arduino API と ESP32 固有の広い公開ヘッダーは分離できる |
| スケッチの一行変更 | 前処理2回1.854、コンパイル1.379、リンク1.539 CPU秒 | コアをキャッシュしても、変更した側の費用は残る |
| 変更なし | リンク1.585、3種類のイメージ処理合計約1.557 CPU秒 | ヘッダーの改善だけでは減らない固定費がある |

「使わない側」の50ファイルは、今回の最小アプリの最終 ELF / map との対応による。一般のアプリから削除してよい50ファイルという意味ではない。また37.186 CPU秒を4で割って、並列ビルドの壁時計時間を予測することもできない。

設定自由度にも独立した問題がある。**アプリごとに変更したい値を含む単一の事前ビルド済み archive は、どの値にも対応する汎用ライブラリにはならない。** 現在の SDK が固定している値を、コアまで追加で事前ビルドすることでさらに固定する設計は、軽量化とは別に評価する必要がある。

採用する実装方式はまだ決めない。以下では、Arduino API を維持しながら内部を変える場合と、現行 ESP32 実装まで維持する場合を分けて判断材料を示す。

## 測り方と数値の意味

CPU秒は、コンパイラードライバーと、そのコンパイラー・assembler・linker 等の子プロセスが消費した user time と system time の合計。Linux の `wait4` によって取得した。待ち時間だけを見る前回の測定と異なり、他の処理に CPU を使われて待った時間をそのままコンパイル費用に含めない。

ソース別は元の `compile_commands.json` を再実行して各3回測定し、順序を固定 seed で入れ替え、最大2プロセスで実行した。ヘッダー比較は各5回。出力先だけを調査用ディレクトリに変え、元のコア・SDK・プロジェクトは変更していない。ソース別の値は各中央値の合計で、一度の全体ビルドの実測時間ではない。

工程別の CLI ビルドではツールの起動を wrapper で記録した。空の build-path の初回1回、変更なし3回、`delay()` の定数変更3回を測定した。初回は4並列。wrapper 自身の Python 起動費用、CLI 自身、シェルのコピー処理、ctags 等は工程別 CPU の表に含めていない。そのため工程の割合は **計測したツール群の CPU 時間に対する割合**である。

ホスト上では別の作業も動いている。変更なしの壁時計時間は6.278 / 11.132 / 6.939秒、定数変更は15.626 / 19.658 / 9.992秒と変動した。以下の順位付けでは、主に CPU 時間と処理回数を用いる。温度、キャッシュ、I/O の影響まで除去した専用機のベンチマークではない。

GCC の工程内訳には別の測定で `-ftime-report` を使った。この機能を入れるとコアの CPU 合計が60.892秒となり、無効時の37.186秒の約1.64倍だった。**ソース別順位とヘッダーの改善率には、この計測機能を無効にした値を使う。** GCC の内部割合は原因を探る補助指標とする。[GCC の計測オプション](https://gcc.gnu.org/onlinedocs/gcc-14.3.0/gcc/Developer-Options.html)

## 初回の費用はどこにあるか

### 実際の CLI ビルドを処理別に分ける

| 処理 | 実行回数 | CPU秒 | 計測対象内の割合 |
| --- | ---: | ---: | ---: |
| コアのコンパイル | 60 | 39.391 | 83.4% |
| スケッチの前処理 | 2 | 1.918 | 4.1% |
| リンク | 1 | 1.692 | 3.6% |
| スケッチのコンパイル | 1 | 1.364 | 2.9% |
| core.a への追加 | 60 | 1.214 | 2.6% |
| bootloader の elf2image | 1 | 0.492 | 1.0% |
| アプリの elf2image | 1 | 0.540 | 1.1% |
| merge-bin | 1 | 0.500 | 1.1% |
| partition の生成 | 1 | 0.117 | 0.2% |
| size | 1 | 0.003 | 0.01% |
| 合計 | 129 | 47.230 | 100% |

この回の壁時計時間は57.113秒。並列なコンパイル、逐次的な archive 操作、計測外の処理、ホストの負荷を含むため、CPU 合計とは一致しない。ソースを直接再実行した中央値合計37.186秒と、この回の39.391秒の違いも、測定方式と実行条件の違いである。

初回を軽くする場合、まず83.4%を占めるコアの内訳を見ればよい。一方、同じ build-path を再利用するだけで、この60回はゼロになる。**コンパイルを回避した効果と、コアの実装自体を軽くした効果は別に記録する。**

### コアのソース別順位

通常フラグで各3回測定。全60ファイルの一覧と各サンプルは [compile-summary.json](research/2026-11-22/deep/compile-summary.json) と [compile-raw.json](research/2026-11-22/deep/compile-raw.json) にある。

| ソース | CPU秒の中央値 | コア全体への寄与 |
| --- | ---: | ---: |
| Esp.cpp | 2.381 | 6.4% |
| WString.cpp | 2.018 | 5.4% |
| HWCDC.cpp | 1.803 | 4.8% |
| USBCDC.cpp | 1.677 | 4.5% |
| HardwareSerial.cpp | 1.657 | 4.5% |
| USB.cpp | 1.596 | 4.3% |
| Print.cpp | 1.566 | 4.2% |
| Stream.cpp | 1.525 | 4.1% |
| USBHost.cpp | 1.518 | 4.1% |
| MacAddress.cpp | 1.500 | 4.0% |
| StreamString.cpp | 1.422 | 3.8% |
| chip-debug-report.cpp | 1.416 | 3.8% |
| Tone.cpp | 1.403 | 3.8% |
| base64.cpp | 1.397 | 3.8% |
| FunctionalInterrupt.cpp | 1.375 | 3.7% |

上位10本で46.4%、上位20本で77.9%。`Esp.cpp` 一つだけを軽くしても削減上限は現在の合計の6.4%であり、一つの巨大な実装だけが原因という分布ではない。

C++ 26本は28.773 CPU秒、C 34本は8.412 CPU秒だった。依存ファイルに `Arduino.h` が現れる18本で25.909 CPU秒、`HardwareSerial.h` が現れる16本で25.568 CPU秒を占めた。これらは重なる集合なので加算しない。標準ライブラリの system header は `-MMD` に出ないため、この方法で STL の依存数は数えられない。

一方、対象チップの条件で code/literal がゼロだった7ファイルは合計約0.251 CPU秒、0.7%だった。**空になる小さな C ファイルを削ることより、重い C++ の共通依存と、未使用でもコンパイルする構造の方が大きい。**

### コンパイラーの内部では何をしているか

`-ftime-report` を有効にした別測定の合計は次のとおり。CPU 合計は GCC 内部で計測する範囲で、外側の driver 等を含む `wait4` の合計とは異なる。

| GCC の区分 | CPU秒 | GCC TOTAL 58.32秒に対する割合 |
| --- | ---: | ---: |
| parsing | 46.48 | 79.7% |
| lang. deferred | 2.02 | 3.5% |
| opt and generate | 9.64 | 16.5% |

さらに下位の項目では preprocessing が15.19秒、template instantiation が5.90秒だった。これらは上表の内訳と重なるため加算しない。計測による増幅があるので「無計測でも正確に79.7%」とは主張しないが、次節のヘッダー除去実験も、公開依存の解析が大きいことを支持している。

## ヘッダーのどの部分が重いか

### 一群ずつ外した比較

`void probe() {}` だけの C++ ファイルを同じ SDK・compiler・最適化設定でコンパイルした。調査用にコピーした `Arduino.h` から指定した include だけを外し、インストール済みヘッダーは変更していない。

| 読み込むもの | CPU秒の中央値 | 完全版からの減少 | 前処理後の行数 |
| --- | ---: | ---: | ---: |
| 完全な Arduino.h | 1.324 | 基準 | 68,611 |
| HardwareSerial.h を外す | 0.955 | 27.9% | 48,404 |
| IPAddress / Client / Server / Udp を外す | 1.221 | 7.8% | 66,516 |
| Esp.h を外す | 1.313 | 0.8% | 68,150 |
| algorithm / cmath と対応する using を外す | 1.167 | 11.8% | 57,914 |
| Serial・Network群・Esp・freertos_stats を外す | 0.798 | 39.7% | 45,841 |
| ArduinoCore-API 1.5.2 だけ | 0.497 | 62.5% | 24,407 |

個別除去の改善率は、共通して読んでいるヘッダーがあるため加算できない。`Esp.h` だけの差は小さく、そこを重点的に削っても大きな効果は期待しにくい。`HardwareSerial.h` の公開依存の方が大きい。

### 独立した include の基礎費用

| include | CPU秒の中央値 | 前処理後の行数 |
| --- | ---: | ---: |
| stdint.h | 0.035 | 229 |
| Print.h と Stream.h | 0.121 | 2,937 |
| FreeRTOS.h と task.h | 0.149 | 6,380 |
| algorithm | 0.477 | 27,909 |
| esp32-hal.h | 0.601 | 30,912 |
| functional | 0.660 | 35,523 |

`HardwareSerial.h` は `<functional>`、USB 関連型等を公開し、`Arduino.h` から読まれる。今回の結果では、FreeRTOS の基本ヘッダーそのものより、STL と広い周辺型の解析が大きい。IDF を全部取り除かなくても、公開型の境界を変えるだけで減らせる部分がある。

ArduinoCore-API の比較には手元の CH32 コアに固定された1.5.2のヘッダーを使った。これは Print・Stream・String 等を含む **公開 API の入口だけ**の比較であり、GPIOやSerial等の ESP32 用実装が完成したコアの比較ではない。完成時の全ビルドが62.5%速くなるという値ではない。

ここから、ヘッダー中心の実装を一律に避ける理由も、一律に採用する理由も出ない。小さい inline 実装で未使用翻訳単位をなくす利点と、使う側が毎回解析する費用を比較すべきである。現状には「大きな公開ヘッダーを読む」「未使用 `.cpp` も作る」の両方の費用がある。

## スケッチを変更したときと変更しないとき

各処理の CPU秒の中央値。各列を別々に中央値化しているため、列の単純和は一回分の合計中央値とわずかに異なる。

| 処理 | 変更なし | delay の定数変更 |
| --- | ---: | ---: |
| bootloader elf2image | 0.505 | 0.511 |
| スケッチ前処理2回 | 0 | 1.854 |
| スケッチのコンパイル | 0 | 1.379 |
| コアのコンパイル | 0 | 0 |
| リンク | 1.585 | 1.539 |
| アプリ elf2image | 0.543 | 0.517 |
| partition | 0.097 | 0.097 |
| merge-bin | 0.510 | 0.508 |
| size | 0.003 | 0.003 |
| 計測したツール群の合計中央値 | 3.221 | 6.363 |

定数変更では前処理とコンパイルが計測対象 CPU の約50.8%、リンクが約24.2%。変更なしではリンクが約49.2%を占める。3種類のイメージ処理はそれぞれ約0.5 CPU秒を使っており、変更なしの場合の合計は約48.3%になる。

改善対象の選び方がここで分かれる。

- **初回・多スケッチ**を軽くするなら、未使用のコア実装と共通の解析費用。
- **編集中の反復**を軽くするなら、薄い公開ヘッダー、前処理の重複、リンクと出力の依存グラフ。
- **変更なしの再実行**を軽くするなら、入力が変わらないリンク・生成処理の省略。

この三つをキャッシュ hit の一つの数字で代表させない。

## 最終バイナリではどこが大きいか

コンパイル費用と保持されるコード量は別なので、最終 ELF も分解した。`.flash.text` は127,964 B、IRAM のコードと vector 等を合わせたコード領域は合計186,332 B。通常の静的データと BSS は21,480 Bだった。

| archive | 保持されたコード B | 保持された通常の静的 RAM B |
| --- | ---: | ---: |
| libc.a | 35,810 | 996 |
| libesp_hw_support.a | 15,706 | 361 |
| libspi_flash.a | 12,920 | 1,428 |
| libfreertos.a | 12,566 | 5,004 |
| libesp_system.a | 12,430 | 855 |
| libhal.a | 11,200 | 16 |
| Arduino の core.a | 10,088 | 1,304 |
| libheap.a | 9,211 | 21 |
| libespcoredump.a | 7,418 | 2,824 |
| libnvs_flash.a | 7,075 | 8 |
| libesp_driver_uart.a | 5,889 | 336 |
| libstdc++.a | 4,383 | 57 |

静的 RAM は実行時 heap、各 task が後から確保する stack、無線開始時の確保を含まない。コードの表は定数文字列等を含まないため、Flash 使用量全体の表でもない。

GNU ld はマージした文字列プール全体の大きさを最初の入力オブジェクトの横に表示する場合がある。その値をそのまま帰属させると、今回も小さな `esp32-hal-misc.c.o` が約34 KBの文字列を持つという誤った分析になる。マージ領域は共有扱いとし、重複するアドレス範囲も二重計上しなかった。選んだ ELF section 計260,100 Bのうち257,130 Bを input section に対応でき、残り2,970 Bは padding 等の未帰属分として残している。

この最小アプリでは、Arduino core 自身の保持コードは全コードの約5.4%だが、コンパイル費用は初回の主要因である。**コアを軽くすることと、最終ファームウェアを軽くすることは同じ順番で効くとは限らない。**

libc の `vfprintf` と `svfprintf` の二つのオブジェクトだけで、コードと literal が25,036 Bあった。core dump のコード7,418 Bと静的 RAM 2,824 B、NVS のコード7,075 Bも、SDK と起動処理の境界を見直す際の具体的な調査対象になる。ただし表の値は保持量で、その機能を外したときの削減量を測った値ではない。他から共有して使う処理もある。

## オプションが何を再ビルドさせるか

同じ60ソースを、指定したマクロだけ変更して前処理し、行番号を取り除いた結果の SHA-256 を比較した。日付・時刻マクロは固定した。**前処理結果が変わる数であり、最終機械語が必ず変わるファイル数ではない。**

| 変更 | 結果が変わったコアのソース数 | その集合の既定設定での CPU費用 |
| --- | ---: | ---: |
| F_CPU 240 MHz → 80 MHz | 1 / 60 | 1.315 CPU秒 |
| ARDUINO_RUNNING_CORE 1 → 0 | 1 / 60 | 1.315 CPU秒 |
| ARDUINO_EVENT_RUNNING_CORE 1 → 0 | 0 / 60 | 0 |
| CORE_DEBUG_LEVEL 0 → 4 | 29 / 60 | 23.051 CPU秒 |
| ARDUINO_USB_CDC_ON_BOOT 0 → 1 | 16 / 60 | 25.568 CPU秒 |
| NO_GLOBAL_SERIAL を有効化 | 16 / 60 | 25.568 CPU秒 |

event core の0は「設定が無効」という意味ではない。core 外の Network 等を含めない今回の集計では結果が変わらなかったという意味である。

F_CPU と loop core は `main.cpp` だけに影響した。同じコア全体の archive を設定ごとに作り直す必要性と、必要な1翻訳単位だけを作り直す必要性には大きな差がある。逆にログや USB CDC の公開依存は広く、事前ビルドを単一化しにくい。

キャッシュキーにオプションを入れることは誤った再利用を防ぐが、**どの値にも対応した一つのバイナリを作れるわけではない。** 条件の組み合わせをすべて配布する案も、選択肢が独立に増えるほど配布・検証対象が増える。設定が1つだけ違うのに全体を作り直す現在の境界も、そのまま引き継ぐ必然性はない。

## いまの SDK によって固定されている設定

今回実際に選ばれた `qio_qspi/include/sdkconfig.h` には1,985個の `CONFIG_` define があった。互換用 alias や派生値を含む数で、1,985個の独立した変更可能オプションという意味ではない。

次の三つに異なる `-D` を渡す前処理実験を行った。

| 値 | 指定した値 | sdkconfig.h を含んだ後の実際の値 |
| --- | ---: | ---: |
| CONFIG_FREERTOS_HZ | 100 | 1000 |
| CONFIG_BT_NIMBLE_MAX_CONNECTIONS | 8 | 3 |
| CONFIG_USB_HOST_CONTROL_TRANSFER_MAX_SIZE | 8192 | 3000 |

生成済みヘッダー側の定義が残った。仮にヘッダーだけを編集して指定値を通しても、既存 `.a` の実装がその値で作り直されるわけではない。構造体、配列、条件付き実装、初期化処理が不一致になる可能性がある。

手元の S3 SDK では、3.3.10 の USB 制御転送上限は256 B、3.3.12と3.3.13では3,000 Bだった。いずれも FIFO 方針は `PERIODIC_OUT` だった。版を更新して上限が変わることと、アプリが必要な値を選べることは別である。

`sdkconfig.defaults` は SDK のソースビルドで設定を選ぶ入口になるが、事前ビルド済みライブラリを実行時に変更するファイルではない。[ESP-IDF 5.5 の設定ガイド](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-guides/kconfig/project-configuration-guide.html)

## プリビルドできる境界を設定の性質から決める

| 設定の種類 | 例 | 適した境界 | 費用と制約 |
| --- | --- | --- | --- |
| 実行時の値でよい | task stack、転送バッファ容量、FIFO 方針の一部 | config 構造体、begin 引数、利用側が供給する buffer | 分岐・間接参照・動的確保等の費用を設計する |
| プロジェクトごとの小さな接続処理 | loop task の core、CPU 起動設定 | 小さい adapter `.cpp` または config object | 基礎部分の archive と設定部分を分離できる |
| 定数化が利益になる小さな処理 | GPIO の固定 pin、短い register 操作 | 小さい inline / template | 使用側でコンパイルするが、未使用分を避けやすい |
| 実装選択そのもの | USB class、BLE host、診断機能 | モジュール単位のソースビルド・選択リンク | 依存を分けないと他の実装も巻き込む |
| layout や内部アルゴリズムが変わる | SDK の接続数、TLS や RTOS 設定 | 一致したヘッダーと必要な依存集合の再ビルド | 一つの汎用 archive だけでは扱えない |
| 本当に固定してよい基盤 | 対象チップの ROM 接続、設定非依存の処理 | 事前ビルド候補 | 固定範囲を必要以上に広げない |

「全部をソースビルド」か「全部を事前ビルド」だけが選択肢ではない。ただし設定を変更する必要のある領域は、ソースで供給するか、実行時設定を受け取れる実装に変える必要がある。

IDF のソースを再ビルドする場合も、単に一つの `.a` を差し替えればよいとは限らない。公開の型や共通設定に影響するなら、その依存先まで再ビルドする。共通 `sdkconfig.h` の変更をすべての `.o` が依存として追っていれば、実際に必要な値が少なくても再ビルド範囲が広がる。設定の公開境界も設計対象になる。

## Arduino API と ESP32 固有の互換性を分ける

| 維持する範囲 | 必要なもの | 維持を前提にしなくてよいもの |
| --- | --- | --- |
| Arduino API | pinMode、digitalRead/Write、時間、割り込み、Serial、Print/Stream/String、SPI/Wire 等の対象 API とその意味 | ESP32 の内部クラス配置、暗黙 include、内部 HAL 名、起動診断 |
| ESP32 固有 API も維持 | Esp クラス、独自 HAL、FreeRTOS task の露出、既存 wrapper 等 | 個別に非互換にすると決めた箇所 |
| 既存の内部・ABI まで維持 | 対象 SDK の型、layout、マクロ、初期化順序等 | 自由度は最も小さい |

Arduino API を使う通常のソースの再利用と、既存の ESP32 `.a` / 内部 API の無変更再利用は異なる。Arduino API を保ちながら、公開ヘッダーを薄くする、Serial の callback 型を変える、起動診断を除く、周辺の所有権管理を作り直す、といった比較ができる。

ただし Arduino API の準拠を名乗る範囲では、pinMode、割り込み、Stream の戻り値等の意味を保つ必要がある。現行 ESP32 実装の癖を再現することを、そのまま準拠条件にはしない。

## スタックと下位基盤を別々に選ぶ

Arduino API、プロトコルスタック、controller driver、PHY、RTOS、heap、割り込みは別の境界である。Arduino API を維持するために、現行 ESP32 のスタックや wrapper を一式維持する必要はない。

| 選ぶ範囲 | 設定自由度とビルドへの影響 |
| --- | --- |
| SDK のスタックを使う | そのスタック内の固定設定を変えるなら、該当実装と依存先を再ビルドする |
| スタックをソースで供給する | アプリごとの設定を反映できる。コンパイル対象と公開ヘッダーを限定する設計が必要 |
| スタックを独自実装する | API・buffer・機能選択の境界を作り直せる。下位基盤は必要な範囲で残せる |
| controller や runtime まで置き換える | 設定と実装の自由度は増すが、起動・割り込み・時間・メモリ等の責任も増す |

buffer 容量や task stack をインスタンスの設定や利用側が供給する領域へ移せば、ビルドフラグに固定する必要を減らせる。一方、コードを消すための機能選択や layout を変える設定は、ソースビルドやモジュール分割で扱う。この判断は個別ライブラリの現行実装との互換性とは独立に行う。

## 実装方式を選ぶための比較対象

数値から比較すべき実験は絞れるが、採用先はまだ固定しない。

| 比較する構成 | 今回の数値から狙える部分 | 残る問題 |
| --- | --- | --- |
| 現行互換のままキャッシュと依存グラフを改善 | 初回60コンパイルの回避、変更なしのリンク・生成処理 | 重い公開ヘッダーと SDK 固定設定は残る |
| 現行コアを分割して必要部分だけコンパイル | 最小例で27.843 CPU秒を使った非保持側の翻訳単位 | 一般アプリでは必要集合が増える。設定・参照の分割が必要 |
| Arduino API を維持した薄い独自コア | 公開ヘッダーの1.324→0.798 / 0.497 CPU秒の差を設計に取り込む | 完成した API 実装と実機検証は別に必要 |
| SDK の一部をソースで供給 | USB host・BLE host 等の設定をアプリ側へ戻す | 型・設定の依存集合を揃えてビルドする必要 |
| 必要な IDF component と独自 stack を組み合わせる | 不要な診断、NVS、VFS、周辺や初期化の到達性を削る | 基盤の責任範囲と保守を明確にする |
| IDF runtime まで減らす | SDK 起動基盤と保持コードの削減範囲を広げる | Arduino API、controller 等の接続、時間・割り込み・heap の検証費用 |

キャッシュ対策は現状の費用を測るための対照構成として必要だが、それを TinyEsp32 の最終設計と決める根拠にはしない。特に、設定をアプリ側へ戻したい部分を追加でプリビルドする案は、速度と設定自由度の両方で比較する。

各レイヤーの実現性、依存関係、保守範囲の詳細は [軽量化レイヤーの調査](build-performance-survey.ja.md) にある。
